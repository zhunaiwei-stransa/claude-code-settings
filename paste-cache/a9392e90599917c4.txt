  But it doesn't always matter

  It depends on whether the sale gets consumed by Match 3 or stays standalone:

  Case A: Sale matches a suggestion (Match 3 consumes it)

  The suggestion already has its own Reservation from Match 1 (date-based), and Match 3 only copies RegiTransaction + RegiTransactionLine — it does not overwrite the suggestion's Reservation:

  if ($suggest['PsProduct']['id'] == $sale['RegiTransactionLine']['item_id']) {
      $suggest['RegiTransaction'] = $sale['RegiTransaction'];       // ← copied
      $suggest['RegiTransactionLine'] = $sale['RegiTransactionLine']; // ← copied
      $suggest['sort_date'] = $sale['sort_date'];
      // Reservation, Menu1/2/3, Resource1 → NOT touched, kept from Match 1
  }

  So the suggestion's Reservation survives. No problem here.

  Case B: Sale is unmatched (leftover, merged at line 2700)

  $suggestions = array_merge($suggestions, $sales);  // leftover sales appended

  These sale rows have no Reservation, no Menu, no Resource. The frontend SuggestionInfoRow.vue must handle these fields being absent — and it does, since all those fields are optional in the component.

  Summary

  Sale.reservation_id = 123  →  Match via $reservationMap  →  has Reservation
  Sale.reservation_id = null →  no match, no fallback       →  no Reservation
                                 └─ if consumed by suggestion: suggestion keeps its own Reservation
                                 └─ if standalone: rendered without Reservation data

  There is no date-based fallback or any other backup strategy for sales. Only reservation_id foreign key is used.
